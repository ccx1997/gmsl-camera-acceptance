# 六路不 OK → 六路 PASS：NX 修复与复现记录

日期：2026-10-19。相机：用户确认 6 台殷创，实测 serializer ID 均为 0xc8。对照平台：此前及本次检查时均能推流的 AGX Orin。两机均为 L4T R35.4.1 / `5.10.120-tegra`。

## 最初状态

- NX 原生 `cam_cfg.ini` 四组均为 sensing / IMX390 / MAX9295 / 1080p。
- 8 个 `/dev/video*` 已注册，但不能据此证明相机链路工作。
- 原 `run.sh` 默认 AGX profile：引用不存在的 `roc-camera-direct.service` 和 AGX 用户目录，并误认为 P0～P5 连续接入。
- 首次验收为 FAIL，37 个失败、9 个警告，未取到有效画面。

## 定位与实测

| 排查层 | 证据 | 对应处理 |
|---|---|---|
| 底层 BSP | 四组 MAX9296 均可读，ID 0x94；I2C mux、PoC、8 个 video 节点存在 | 沿用 NX 已有厂家内核与设备树，没有刷 AGX 镜像 |
| 同轴链路 | 默认 6 Gbps 时 8 路不锁；逐条改为 3 Gbps 后 6 路稳定锁定 | 使用与当前批次匹配的初始化库 |
| 实际接线 | 30A/30B、31A/31B、32B、33B 有相机，32A/33A 无相机 | 采用物理拓扑 0,1,2,3,5,7；新机器重新探测 |
| 相机端 | 六台 serializer ID 为 0xc8，AGX 正常链路也为 0xc8 | 使用 isx031std / extra_mode=2，未按品牌盲切 extra_mode=11 |
| CSI lane | AGX 四 lane，NX 当前设备树两 lane | NX `lane_mode=32`：4x2 D-PHY / 2 lanes |
| 多路带宽 | 2-lane/1500 Mbps 配置虽出图，但出现 CHANSEL_SHORT_FRAME 与 corr_err | 每 lane 改为 2400 Mbps 后错误消失；不是改同轴 GMSL 速率 |
| 节点与 VC | 厂家库按实际物理节点初始化 video5/7，单独 B 链路却输出 VC0；这两节点期望 VC1 | 保持奇数 video 映射，修正单 B 组四项输出包 VC 位 |
| 网络推流 | 原系统缺 rtspclientsink | 补两个 Ubuntu 包，部署 MediaMTX、硬件编码、15 Hz 触发 |
| 自动验收 | 错误机型 profile 导致额外误报 | 生成 NX 的路径、端口映射、库搜索路径和文件指纹 |

单 B 链路修正的包映射为：`0x048e: 0x1e→0x5e`、`0x0490: 0x00→0x40`、`0x0492: 0x01→0x41`、`0x0494: 0x12→0x52`。与已正常工作的双链路 B 通道使用同样的 VC1 目的映射。仅对所在组 A 未接、B 已接时应用，并先检查低六位包类型、写后读回验证；不覆盖未知表项。

## 已经复现的结果

手工修复阶段：6 路 RTSP 实际解码均成功；1920×1536 H.264；30 秒窗口内每路约 14.97～15.04 fps；采集错误为零。`run.sh` 在 15:14:49 的报告为 PASS，6/6 检测及出图。

仓库部署工具阶段：已用 `nx/probe.py` 在同一 NX 上重新探测，并从仓库内置包安装到全新的 `/opt/gmsl-nx`，不依赖旧手工目录里的程序。15:45 的 `run.sh` 再次 PASS；所有图片均来自 RTSP 解码。安装器内置 30 秒检查记录为六路约 15 fps、内核采集错误 0。

实机验证也修正了“target 停止返回后，子进程尚未完全释放设备”的时序问题：部署、初始化和探测在写配置前最多等待 12 秒，再次确认空闲。SSH 输出中断不会因为状态打印失败而中止硬件配置事务。

## 后续开机出现 cam2/cam3 绿屏（同日 17:45 排查）

本次开机约 28 秒起，CSI1 的 VC0/VC1 持续报告 2500 ms 采集超时。cam2/cam3 对应 bus31、video2/video3，共用一组 MAX9296。两台 serializer ID 均为 0xc8，链路锁定、PoC 和关键配置寄存器正常；运行文件校验全部通过，但两路输出纯绿画面，实测约 1.6 fps，另外四路约 15 fps。因此 `systemctl active`、RTSP `ready` 或“能解码一张图片”均不足以证明采集健康。

仅重启两路采集、补发一次手动 deskew、切换该组 CSI 输出均未恢复；这些临时寄存器操作均已恢复原值。随后对这组相机重新上电，并用仅含 deserial_1/port_2/port_3 的厂家配置重新初始化，两路恢复真实画面，采集超时消失。

**单组配置仍会操作全局触发器。** 厂家初始化将共享 CPLD 改到 30 Hz，并与仍持有串口的触发服务发生读应答竞争。随后重新启动触发服务和六路推流，恢复目标 15 Hz。最终 30 秒检查：六路 14.999～15.000 fps、内核采集错误 0；六路 RTSP 解码成功，cam2/cam3 实拍图已人工确认不是绿屏。

17:55 的完整验收仍因五分钟窗口内的旧采集错误判为 FAIL；保留日志、等待旧错误自然移出窗口后，`results/20261019-175608/` 的完整验收为 PASS，6/6 检测及出图，没有缩短日志窗口或清空错误记录。

目前确定的是本次开机后的共组采集异常及有效恢复方法，尚未确定上电、触发和 CSI 时序中的具体根因；不能据此断言相机损坏、线束故障或 deskew 是根因。没有修改持久运行配置或增加未经验证的自动重试。连续冷启动可靠性仍未验证通过。

现场证据保留在 `/home/ccx/gmsl-nx-runtime/diagnostics/20261019-cam23-green/`，含故障前日志、各阶段检查、恢复后 RTSP 实拍图；这些现场文件不入 Git。日常恢复采用操作手册的整套停止/初始化/启动流程，不在其他流运行时单独调用厂家初始化程序。
